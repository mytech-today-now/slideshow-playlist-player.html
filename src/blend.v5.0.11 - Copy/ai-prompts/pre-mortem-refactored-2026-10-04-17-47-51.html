Finding 01 | Source claim 11

File picker identity can merge distinct same-name files

Type and triage

Status: Open. Priority: P2. Severity: 2, moderate data integrity risk. Likelihood: Possible when files are added without stable relative paths.

Current evidence

app.js:4622-4659 prefers a source URL or normalized path for identity. When neither exists, sameIdentity falls back to it.name === name at line 4645. The subsequent size check accepts equal size, or missing size, at line 4646. A match returns the existing record rather than adding the selected handle.

Testable assumption: two different files with the same name and byte length, added through a picker without path hints, take this fallback and one file is omitted from the library. This path is visible in source; the browser reproduction was not run.

Why it matters

Users may select two different clips with the same filename from separate directories. If the browser picker supplies no relative path, the second file can disappear behind the first library entry.

Recommended mitigation

Deduplicate only when a stable source URL or normalized path matches. When identity is ambiguous, retain a distinct library item or ask the user instead of using filename and size as proof of identity. Preserve folder path hints and the existing persisted schema.

Implementation prompt

Inspect Add Files and Add Folder callers of ensureHandleInLibrary. Reproduce two distinct same-name, same-size synthetic files with and without path hints. Change the smallest identity helper so equal filename and size alone do not collapse an ambiguous local file. Keep exact-path and identical-source deduplication behavior, preserve pathHint and IndexedDB compatibility, and do not hash entire media files as an implicit workaround. Add focused regression coverage and a browser workflow test for separate selected handles. Run the focused checks and report only results actually observed.

Regression and baseline checks

  1. Two same-name, same-size records with distinct paths remain separate.
  2. Equal normalized path continues to reuse the existing record.
  3. Unknown file size does not turn a name-only collision into confirmed identity.
  4. Existing folder imports retain relative path hints and playback still resolves both items.

Acceptance criteria

  1. Ambiguous local files are not merged solely because name and size match.
  2. Stable path and URL deduplication contracts remain covered and pass.
  3. Export, relink, selection, and reload preserve both distinct records.

Confidence

High for the equality branch; medium for user impact until reproduced in a browser.

Finding 02 | Source claim 12

Directory scans hide skipped branches

Type and triage

Status: Open. Priority: P2. Severity: 2, moderate import completeness risk. Likelihood: Possible when an entry iterator rejects partway through a folder.

Current evidence

app.js:4577-4611 catches errors for a directory branch, logs a sanitized warning, and continues. It returns only the collected file handles. app.js:4544-4565 then displays added and existing counts, without a skipped-branch count or incomplete-scan notice.

Testable assumption: a permission or read error in one nested directory can produce a success-looking partial import. No failing directory fixture was executed.

Why it matters

A user can finish an import believing the selected folder was fully scanned while media from a nested branch was skipped.

Recommended mitigation

Carry a scan summary with discovered handles and sanitized skipped-branch counts. Preserve successful files, but report partial completion and offer a retry path. Do not log local paths or file names.

Implementation prompt

Trace every walkDirectoryForMedia caller. Add an additive scan summary or progress callback that records branch failures without exposing paths. Update folder import and missing-media relink copy to distinguish complete, partial, canceled, and empty scans. Keep found files and cancellation behavior intact. Add a fake directory handle whose nested iterator rejects after returning a file; assert partial status reaches the user while the file remains importable. Cover an empty complete scan and a fully successful scan as baselines.

Regression and baseline checks

  1. A nested branch failure is counted and produces a partial-scan notice.
  2. Files discovered before and after a failed branch remain available.
  3. A complete scan keeps the existing success message.
  4. Cancellation remains distinct from a read failure and does not report success.

Acceptance criteria

  1. Callers can distinguish a complete scan from a partial scan with skipped branches.
  2. Partial results are retained and the user can retry without duplicate media.
  3. Logs contain only sanitized operation and error categories.

Confidence

Finding 03 | Source claim 13

IndexedDB startup can remain blocked without recovery feedback

Type and triage

Status: Open. Priority: P2. Severity: 2, startup availability risk. Likelihood: Uncommon, especially during a version upgrade with another open tab.

Current evidence

app.js:3138-3162 handles the open request's upgrade, success, and error events, but has no onblocked handler or bounded wait. bootstrap awaits openDB() at app.js:11193; the DOM-ready registration at app.js:11292-11295 passes bootstrap directly and has no rejection handler.

Testable assumption: a version change held by another tab can leave this tab without an actionable startup message; an open failure can become an unhandled bootstrap rejection. No two-tab upgrade was run.

Why it matters

The app needs its database before hydrating its library and wiring controls. A blocked upgrade or failed open can prevent startup without telling the user how to recover.

Recommended mitigation

Add bounded blocked/open failure state with a clear instruction to close older Blend tabs and retry. Keep the app fail-closed for persisted data and avoid rendering a false empty library.

Implementation prompt

Review openDB, bootstrap, and versionchange handling. Add explicit blocked and error outcomes with a bounded timeout and accessible retry or recovery copy. Do not silently continue with empty state or overwrite the existing database. Add deterministic tests for success, error, blocked timeout, and late success; add a two-page browser test for a blocked version upgrade where the harness permits. Preserve version 5 stores and migrations.

Regression and baseline checks

  1. A blocked open reaches a visible, actionable recovery state before timeout.
  2. An open error is caught by bootstrap and does not produce an unhandled rejection.
  3. A late successful request does not double-initialize controls.
  4. A normal open still hydrates saved state and keeps current schema migrations.

Acceptance criteria

  1. Every database open settles or reaches a bounded recovery state.
  2. The user is told how to resolve a blocked upgrade without data loss.
  3. No failed open is presented as a successful empty start.

Confidence

High for the missing handlers; medium for the exact browser failure outcome.

Finding 04 | Source claim 15

The accessible list row omits the current playback state

Type and triage

Status: Open. Priority: P2. Severity: 2, accessibility information gap. Likelihood: Consistent for assistive technology that reads the row label.

Current evidence

app.js:6426-6446 calculates isCurrent and adds a visual CSS class, but the row's accessible label includes name, availability, and timing only. The row does not set aria-current. The only nearby playback announcement found is a generic experience-level toast at app.js:7219.

Why it matters

A screen-reader user navigating the list cannot identify the item currently playing from the row's accessible state, even though sighted users get a visual highlight.

Recommended mitigation

Implementation prompt

Add a semantic current-playback signal to exactly the active row and clear it from the previous row after advance, stop, switch, or relink. Keep row selection semantics separate from playback state. Add automated accessibility assertions for both layers, plus a manual screen-reader review note rather than claiming that automation is a human audit.

Regression and baseline checks

  1. Current row exposes the state in its accessible name or aria-current attribute.
  2. Next, Previous, stop, and experience switch update the state correctly.
  3. Selected state remains independent and is not overwritten by current playback state.
  4. Unavailable rows keep their existing accessible error detail.

Acceptance criteria

  1. Current playback is programmatically available for both layers.
  2. Only the current row in a layer carries that state.
  3. Keyboard selection, row virtualization, and unavailable-item descriptions remain intact.

Confidence

High for the missing row-level semantic; a screen-reader audit was not performed.

Finding 05 | Source claim 17

A failed reset can still sign the user out

Type and triage

Status: Open. Priority: P2. Severity: 2, partial-action reporting and recovery risk. Likelihood: Possible when snapshot or database deletion fails after session clearing.

Current evidence

app.js:8281-8299 calls clearLocalSession() before creating the recovery snapshot. app.js:8308-8319 can then fail IndexedDB deletion and show “Could not clear saved data” without saying the saved session was already removed. The README at README.md:659-665 describes selected LocalStorage keys and reset behavior, but does not document this partial outcome.

This is a local session clear; no remote logout is implied by the inspected path.

Why it matters

The reset can partially succeed while presenting a generic failure. Users may believe they remain signed in, or repeat a destructive operation without understanding which state changed.

Recommended mitigation

Either defer clearing the session until the IndexedDB deletion is committed, or provide explicit partial-reset copy when session removal succeeds but database reset fails. Keep recoverable database state and avoid claiming a full reset.

Implementation prompt

Trace reset ordering, rollback, and current tests. Make the smallest change that ensures each failure outcome names whether local sign-out happened and whether saved Blend data remains. Keep this operation local-only and do not add a network logout. If session clearing stays before database deletion, show an explicit partial-reset message on snapshot or delete failure. Add failure-injection coverage for snapshot, delete, session-storage removal, and retry; preserve other tabs' recoverable data.

Regression and baseline checks

  1. Database deletion failure reports that the local session was removed if it was.
  2. Session storage failure stops before deleting other Blend data.
  3. Successful reset reports completion only after all promised steps finish.
  4. Retry does not restore a cleared token or falsely claim remote logout.

Acceptance criteria

  1. Every reset failure message truthfully describes local session and saved-data state.
  2. Recoverable data is retained on failure and available for retry.
  3. No reset message implies remote logout unless a remote logout call is added and verified.

Confidence

High for the operation order and generic error copy; medium for failure frequency.
